The Problem

In every Transport Analytics deployment, data quality issues accumulate silently: ghost shipments (stale-delete CDC events), orphan ORDER_SHIPMENT records, date sequence violations, and zero-weight orders. These corrupt On-Time Delivery metrics and mislead supply-chain planners.

Identifying and fixing one RED KPI today requires a senior DBA with SQL expertise, 4–8 hours per week, and deep Transport Analytics domain knowledge. Business analysts see a red dashboard but cannot act on it without engineering escalation.

Solution Statement ≤500 words — Challenge Requirement

Problem. Transport Analytics deployments accumulate silent data quality failures: ghost shipments created by stale-delete CDC events, orphan ORDER_SHIPMENT rows that break referential integrity, impossible date sequences in tracking feeds, and zero-weight orders that distort cost calculations. These defects corrupt the On-Time Delivery percentage — the primary supply-chain SLA metric — and produce misleading dashboards that planners and finance teams act on without knowing the data is wrong.

Target users. Six personas across a typical Transport Analytics operations team: Data Engineers (pipeline integrity, CDC correctness), Data Stewards (field conformance, null policy), Operations Managers (tracking completeness, OTD accuracy), Finance Analysts (weight and cost accuracy), Logistics Planners (carrier SLA monitoring), and Supply Chain Managers (end-to-end OTD and re-assignment rates). Today all six must escalate to a senior DBA before any investigation can begin.

Expected outcomes. Any of the six personas can open the dashboard, click Run Monitor Agent, receive a plain-English alert addressed directly to their role, click Explain to see the root cause in plain English, click Generate Fix to preview a safe corrective SQL statement, and click Apply Fix to execute it — all in under 60 seconds, with no SQL knowledge required. Quantified impact: investigation time drops from 2–4 hours to 45 seconds; the weekly DQ review cycle shrinks from 4–8 hours to under 5 minutes; root-cause identification drops from 1–2 hours to 10 seconds. The platform runs on a live Databricks SQL warehouse and is fully repeatable — the Monitor Agent can be re-triggered on every new data load, turning a weekly fire-fighting exercise into a continuous, automated quality gate that any analyst can operate.

Three-Tier Agentic Pipeline

Tier 1
Monitor Agent
Reads all 15 live KPI values from Databricks. IBM Bob translates numbers into plain-English, persona-addressed business-impact alerts. Stored in dq_alerts.
Tier 2
Root-Cause Agent
Fetches the actual failing records (up to 20 rows). IBM Bob analyses the records, identifies the root cause pattern, and returns root_cause, pattern, and suggested_sql.
Tier 3
Remediation Agent
IBM Bob writes a safe, targeted SQL fix. Human approves before execution. On approval: SQL runs, KPIs recompute, card animates GREEN. Safety guards block DROP/TRUNCATE.
Supporting
Summary Agent
Generates a 3-4 sentence executive summary of current DQ health on every page load. Mentions overall score, most critical RED KPI, and one positive finding.
Supporting
Chat Agent
Answers natural-language questions (e.g. "Which orders are causing the ghost mapping?") with KPI + history + alert context. Cites and highlights specific KPI cards in the reply.

Technical Statement ≤500 words — Challenge Requirement

Bob API integration. All five agents call IBM Bob through a shared agents/bob_client.py wrapper. Authentication uses OAuth 2.0 — the wrapper reads a DPAPI-encrypted token from the Bob IDE's local SQLite credential store (_dpapi_decrypt()), or falls back to a plain BOB_API_KEY environment variable. Every HTTP request sets User-Agent: bobshell/1.0.6 (required to pass Cloudflare WAF inspection at the IBM endpoint). The model is openai/gpt-oss-20b. All calls retry up to three times with exponential back-off before raising BobAPIError.

Agent-by-agent AI interactions.

  • Monitor Agent — receives a dict of 15 live KPI values from Databricks; sends them to Bob with a persona-mapping system prompt (temperature 0.2); Bob returns a JSON array of alert objects each containing kpi_id, severity, message (plain-English, persona-addressed), and suggested_action. Results are written to workspace.otm.dq_alerts.
  • Root-Cause Agent — receives up to 20 failing rows fetched from /api/drilldown/<kpi_id>; sends them to Bob with a root-cause system prompt (temperature 0.2); Bob returns a JSON object with root_cause, pattern, affected_count, suggested_action, and suggested_sql.
  • Remediation Agent — receives the root-cause dict; Bob drafts a safe, targeted UPDATE SQL (temperature 0.2), returning sql, risk_level (LOW/MEDIUM/HIGH), row_estimate, and explanation. Before execution, the wrapper blocks any SQL containing DROP, TRUNCATE, or DELETE without a WHERE clause.
  • Summary Agent — receives all 15 KPI values; Bob writes a 3–4 sentence executive summary (temperature 0.3) naming the overall score, the most critical RED KPI, and one positive finding.
  • Chat Agent — receives the user question plus KPI snapshot, alert history, and conversation history; Bob answers in natural language (temperature 0.3), returning reply and a cited_kpis list used to trigger pulse animations on the referenced KPI cards.

JSON reliability. Every structured agent uses parse_json_response(), which strips markdown code fences (```json … ```) that the model sometimes wraps around its output before passing the string to json.loads(). If Bob is unreachable, each agent switches to a pre-written fallback dict (FALLBACK_MESSAGES, FALLBACK_ANALYSES) so the full demo runs without credentials.
